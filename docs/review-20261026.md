## 按优先级排列的问题

### P1：预约执行未重新执行日累计强验证规则

位置：`banking_agent/bank.py` 的 `_risk`（约 794 行）和 `_run_schedule`（约 1102 行）。

普通转账按实际当日累计判断红黄级别；预约创建按同一执行日期的已预约金额判断。预约到期执行只重新检查安全锁定与可用余额，没有把该日已发生的普通转账和预约金额合并，再决定是否需要强验证。

复现：10 月 26 日创建 10 月 27 日转 1000 元的预约，黄色确认；27 日先普通转账 300 元，黄色确认；再调用正常 `run_due('alice')`。预约返回 `succeeded`、`forced=false`，`daily_transfer_cents=130000`。不需要调用演示“立即执行”接口就能复现。

影响：违反赛题“日累计 > 1000 元需强验证”的核心要求。原预约虽然经过本人确认，但没有经过超过累计阈值所需的强验证。

处理：到期执行前在同一事务内重算实际当日累计；需要升级验证时进入待验证状态，完成与该操作绑定的强验证后才能扣款。补充“预约与普通转账混合”“月度预约滚动”“多个预约同日到期”的回归用例。

### P1：当前提交说明与安全、答辩材料相互矛盾

`docs/submission.md` 仍写“当前没有远端地址”，并把资金冻结、预约、AA、理财列为未完成；`docs/requirements.md` 的 BIZ-007/008 同样过期；安全自评仍按旧能力边界说明。代码和 README 已新增这些模拟业务，远端也已配置为 `https://github.com/DragonFlamee/bankagents`。

旧讲稿最后一页仍说理财、预约、AA、冻结未实现，测试数字仍为 140。现存 PPT、视频对应更早界面，不能证明新增场景的当前效果。作品简介目前 163 字，符合 200 字以内，但只突出旧版三类业务。

影响：评委读不同材料会得到不同的完成范围，无法快速核验安全边界。不要直接把历史测试与本轮数字混加，也不要把模拟冻结说成真实银行资金冻结。

处理：以一个固定提交统一 README、需求追踪、算法、安全设计、自评、作品简介、PPT、讲稿和视频；所有新增业务明确标为模拟。

### P2：手机图表缩放后文字过小

位置：`apps/frontend/src/viz.tsx`、`Runway.tsx` 的 SVG 图表。390px 视口下按文本字号乘 SVG 屏幕变换矩阵测量：账单桑基图标签约 4px，部分数值约 3.5px；资金日程刻度约 6.5px。页面虽然没有整页横向溢出，图表文字仍难以阅读。部分图表明细依赖鼠标悬停，键盘与触控等价体验还需补充。

处理：为手机使用精简布局，保留正常字号；复杂图放进有明确提示的横向滚动容器，或提供同数据的明细列表。日期、金额与预测依据不能仅藏在 hover 提示里。

### P2：手机登录入口被展示内容推到首屏之外

390 × 844 下，登录表单位于约 730px 之后，“进入拾迹银行”按钮需要进一步向下滚动。首屏主要是品牌文案与示意工作流。

处理：手机优先展示账户和登录按钮，把示意流程收起或放到表单后；保留清晰的“模拟账户”说明。

### P2：新增巡检脚本不能直接在 Windows 按 README 复现

`evals/scenario-tour.cjs:24` 写死 `.venv/bin/python`，Windows 实际入口是 `.venv/Scripts/python.exe`；`chromium.launch()` 又依赖另行安装的 Playwright 浏览器。本轮在临时副本中适配 Python 路径并指定本机 Edge 后才完成巡检，没有改原脚本。

处理：按平台选 Python，明确浏览器安装或已有 Edge 的配置方式；增加服务器启动失败的错误处理，避免评委复现时长时间等待。

### P3：演示账户姓名存在不一致

登录页和新播种数据把 bob 称为“陈昱”，`banking_agent/api.py` 登录与会话接口仍返回“陈一航”。测试切换账户时会看到不同名字。接口应从同一账户数据源读取。
