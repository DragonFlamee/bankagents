# 信息架构与两个布局方案

在内容审计后制定，早于本轮 UI 实现。产品事实、后端状态和核心操作均以审计中的证据为准。

## 共同的三级结构

一级：任务、一个真实状态、业务结果、不可隐藏的警告与授权、下一步。
二级：查看执行详情 → 步骤、时间、完整业务结论、回执与依据、任务控制。
三级：技术日志 → 原始工具调用、参数、节点ID、内部状态、模型元数据与用量。

复杂依赖图是二级中的可选调试视图，节点原始数据是三级。单节点只显示一条步骤摘要；少量顺序节点用列表，不自动开图。审计页面本身用于查记录，可显示业务事件名与时间，展开后保留原始代码和哈希。

## 方案 A：任务正文 + 按需执行详情（推荐）

```
深色导航 216       顶部：页面定位             搜索  模拟环境  刷新
新建任务           ─────────────────────────────────────────
五个导航           向李娜转账 ¥300             等待用户确认
最近任务           核对收款人、付款账户、金额和有效期
                   [确认转账] [取消操作]
                   查看执行详情 → 按需打开右侧面板
                   业务需求输入
                   （宽屏面板展开才占右侧空间；手机以独立详情窗口展示）
```

默认一个主要任务面，保留聊天式输入能力，但没有重复的聊天角色和重复标题。授权直接在正文，结果不依赖用户打开日志。右侧是有目的的详情面板，关闭后归还空间。空态没有侧栏。

删除空执行栏/三阶段教程、Agent头像行、重复新建、宣传页脚、总额重复摘要卡。合并任务标题/指令、一级状态/操作状态。将步骤/时间/回执移到详情，模型用量和原始调用再进技术日志。

推荐理由：当前应用的主要场景是单次查询或带确认的短任务，一列可把核对字段放到最清楚的位置；多步骤和审计仍可访问。长期使用无需在窄右栏寻找授权，也不会把单次查询误解成复杂图工作台。

## 方案 B：任务收件箱 + 办理分栏

```
窄品牌导航       任务队列 280              办理内容
导航图标/文字    待确认 / 运行 / 历史       选中任务、状态
                任务摘要列表              核对字段、确认
                搜索与筛选                结果与步骤（折叠）
```

此方案把历史与审批合并成队列，结果和执行步骤置于同一办理窗。需要删除独立最近任务区域，合并历史/审批入口并改造当前五路由的导航关系；适合高频并行处理大量任务的操作员。视觉采用石墨导航与更密集列表，信息拓扑明显不同。

未选理由：个人模拟账户主要是提出目标并核对，现有任务量最多30条；常驻第二列队列会重现空间争夺，也改变已有五模块习惯。用户要求保留核心业务，方案A结构变化足够且风险更可控。

## 选定视觉与交互方向

在内容和结构落实后采用深海军蓝导航、白色主任务面、冷灰辅助面、克制实心品牌紫。金额 tabular-nums；正文16px附近，操作与记录14px，元数据13px。主区 max-width 920，展开详情时仍保留足够的金融字段宽度。普通区域以间距分组；只有实际核对边界和浮层使用边框/阴影。

复用 React/TypeScript、现有API和 Motion；详情关闭即不可聚焦，Escape恢复触发点，图支持自动适配/平移/缩放/节点键盘查看。移动端先任务结果和授权，技术信息通过全屏详情查阅。

参考取舍：[Linear](https://linear.app/now/behind-the-latest-design-refresh)支持降低导航与辅助信息竞争，[Mercury Command](https://mercury.com/blog/introducing-mercury-command)强调以账户数据与原有权限完成工作；不是复制产品功能。[渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)用于推迟不常用信息，[GOV.UK Summary List](https://design-system.service.gov.uk/components/summary-list/)用于清楚核对金融字段。现有SVG图足够承载最大12节点，参考[React Flow Controls](https://reactflow.dev/api-reference/components/controls)的控件职责，不为改造引入第二套图引擎。
